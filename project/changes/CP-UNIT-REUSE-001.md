# CP-UNIT-REUSE-001｜单元样例作为主体游戏可复用模块

状态：`PROPOSED`；日期：2026-10-01。来源：用户要求地面、树木、房屋、精灵、特效尽量形成独立的 Cocos Creator 工程产物，支持并行打磨和反复迭代，并与主体游戏保持逻辑、UI 细节一致。

## 现状与问题

`UNIT-SAMPLES-001` v0.1 将 U01–U09 放在 `UnitSamples.scene`，主要由单个 `UnitSampleGallery.ts` 动态生成和管理。这满足当前菜单验证目标，但资源、行为和演示界面尚未分离，不能直接证明单元成果可被主体游戏复用。

## 拟议目标

1. 地面、树木、房屋、精灵、特效分别有独立可打开、可运行、可重置的 Creator 演示入口。工程可采用同一个 Creator 项目中的独立 Scene、Prefab、脚本与资源目录；是否需要物理上拆成多个 `.creator` 项目，由 Tech Lead 评审导入成本与资源引用后确定。
2. 各单元的正式运行逻辑和可复用 Prefab/资源作为主体游戏的同一份来源。演示入口只负责测试控制、参数展示和诊断，不复制主体游戏逻辑。
3. 主体游戏与单元样例消费同一份产品规则、状态定义、输入行为、视觉与 UI 组件规格。演示专用按钮或诊断数据须明确标记，不能被误认为主体游戏界面。
4. 资源与逻辑须有稳定接口和引用关系，使地面、树木、房屋、精灵、特效可分别迭代；跨单元接口变化经 Tech Lead 评审，并检查受影响单元及主体游戏。
5. 每类单元至少验证一次“修改单元源产物 → 演示入口生效 → 主体游戏集成入口生效”的同源链路；差异须逐项记录。旅客未具备正式四方向资产或对象未具备正式分层资产时继续标为占位。
6. 所有需要动态表现的精灵，包括角色、建筑、树木等，目标采用骨骼动画。静态对象不因所属类别被强制添加无意义动画；哪些状态需要动态表现由产品、美术和技术在单元规格中列明。
7. 每个骨骼动画对象的图像元素须规划为**一张贴图/图集**，容纳该对象实际需要的动作和状态；需要行走转向的旅客还须容纳四方向资源。店铺和店长不以四方向为交付要求。骨骼数据及贴图是可复用源产物；演示入口与主体游戏引用同一版本。若单张图无法满足目标平台的尺寸、内存或画质约束，须提交明确的技术评审和变更请求，不能自行拆图或降低已批准的方向覆盖。
8. 每次输出美术资源前，Art 与 Tech Lead 共同确认图集排布、贴图尺寸、留白与裁切、适用对象的方向覆盖、材质/混合模式、动态合批条件和目标设备性能预算；记录版本、预估或实测的 DrawCall、显存/内存影响及结论。没有共同确认记录的资源不进入正式交付。
9. UI 优先复用同一份组件、图标、状态资源与字体规格，单元演示和主体游戏的共用界面元素须同源。图片产出前记录参考来源及风险检查；系统字体和美术字体均须核验实际用途的许可。美术字体可在许可允许时改造，但修改本身不构成版权风险豁免。

## 建议交付与门禁

- Product：确认各单元进入主体游戏时的行为语义和验收点，不新增未经批准的玩法。
- Art / UI / VFX：分别确定资产、界面组件和特效的源文件、Prefab/资源边界及版本标识；Art 与 Tech Lead 在每次动态资产输出前完成图集合批评审。
- Tech Lead：评审模块边界、共享接口、Creator 资源依赖、独立工程形式和集成方式，形成技术设计；给出目标平台贴图尺寸与性能预算，并验证骨骼动画及合批条件。
- Client：在技术设计获批后拆分 v0.1 集中脚本，提供各单元演示入口与主体游戏集成入口。
- QA：按同源链路、单元独立运行、跨单元回归、主体游戏一致性、旅客四方向动画覆盖和目标设备性能出具测试结果。
- Producer：跟踪各阶段 Artifact 版本与用户审批。当前 v0.1 样例不因此自动验收为可复用成果。

本提案涉及跨角色资产与代码契约，应按当前游戏的正式变更流程评审并获用户批准后成为项目决策及下游开发输入。
