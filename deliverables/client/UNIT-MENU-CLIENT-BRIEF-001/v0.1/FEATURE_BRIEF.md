# 百鬼夜市七项菜单｜客户端编码前概要 v0.1

任务：`UNIT-MENU-CLIENT-BRIEF-001`。输入为已获用户批准的 `UNIT-MENU-PRODUCT-001 v0.2`、`UNIT-MENU-TECH-DESIGN-001 v0.2`、`UNIT-MENU-ART-DESIGN-001 v0.2`、`UNIT-MENU-UI-SPEC-001 v0.2`、`UNIT-MENU-VFX-SPEC-001 v0.2`。本版仅定义开工切片；没有新七项运行代码、正式 Creator UUID 或目标设备实测。须与 QA `UNIT-MENU-QA-PREBUILD-001 v0.1` 一同提交用户审批后才可编码。

## 1. 目标与范围

在现有 Cocos Creator 3.8.8 工程中建设七个顶层 Lab 菜单，第三项再分 `3A 孟桃`、`3B 幽灵顾客`。每个对象是可单独编辑的正式 Prefab；独立样例和组合场景引用同一个 Prefab、同一状态控制和同一正式资源。第 1 项只显示背景基底与 Lab 控件；第 7 项从第 1 项相同背景与镜头参数出发，动态增删已批准对象，供遮挡与资源身份比对。未来主体游戏接入时再复验同一 ID/UUID/版本；当前不声称第三入口已测。

七项的可执行切片见 [场景与 Prefab 方案](SCENE_PREFAB_PLAN.md)。本阶段不实现服务端、经营/订单/收益、顾客 AI、完整六店、主线剧情或正式对白。Lab 控件仅供观察；正式身份卡、孟桃对话容器及对象表现组件需可被未来主体复用。旧 `UnitSamples.scene`、`UnitSampleGallery.ts`、`assets/demo/` 仅保留历史审计，不进入新七项依赖；旧九项菜单与四方向瓦片机制不充作新成果。

## 2. 现有能力与新增边界

现有项目已锁定 Creator 3.8.8，开启 `2d`、`animation`、`spine-3.8`，设计画布为 720×1280。旧脚本里有 SpriteFrame 数组和镜头演示，但它依赖 45° 瓦片、旧 Demo PNG、九项集中控制和常数平移边界；只能借鉴输入/动画 API 用法，不能复用旧场景数据、形体或资源。新实现沿用 Creator 原生 Scene、Prefab、SpriteFrame、Animation/Spine、UI 事件、AssetManager 能力，不引入大型依赖或新网络/API Contract。

建议新增轻量职责：Lab 路由与控制层只负责菜单、进入/返回/复位、操作转发和诊断；共享场景相机控制只负责水平拖拽、缩放、合法视口；正式对象组件各自负责自己的状态、动画与附属效果；资产登记校验读正式 ID、`.meta` UUID、版本哈希和合法实例覆盖。每个职责仅在真实重复时抽出公共层，避免再次形成一只管理全部九项的类。依赖方向为 `Lab 控制 → 正式对象公开动作/状态接口 → Creator 资源`；正式对象不反向依赖 Lab 菜单。所有接口名与参数只在实施时和 Tech 复核，不在本稿自造跨模块数据 Contract。

## 3. 关键行为与输入

| 范围 | 客户端实施合同 | 对应产品验收 |
|---|---|---|
| 菜单与生命周期 | 仅七顶层、第三项 3A/3B；每项 `enter → active → reset/leave`。进入只装载本项获批对象，返回先令会话令牌失效、停异步、动作、VFX、计时与订阅，再卸载。重进恢复可预测初态 | A01、A02、B08 |
| 空底板与组合 | `STREET_BASE_01` 在 1/7 为同一 Prefab UUID、同一相机参数；组合初态零店/人/凳/树花灯；各对象任意顺序加减，复位后回空底板 | A03、B01、B08、D03 |
| 店铺 | `MT_SHOP_01` 静态店身与 `MT_SHOP_MOTION_01` 骨骼动件；暖灯、邻近墙柜受光和地面暗部/投影成对变化。一店一组效果，重复触发不叠，移除回基态 | B02、D01 |
| 孟桃 | `MT_CHAR_01` 单视角骨骼 idle→一轮工作演示→idle；重复触发不叠，挂点反馈随实例退出；腰牌“孟”只在角色腰牌 | B03、D01 |
| 幽灵 | `UG_GHOST_01` 单原创朝向透明 SpriteFrame 序列；`move`/`run` 为各自约 4–6 帧的首轮循环预算，`happy`/`sad` 为一次动作加保持，`sit` 为接近→进座→稳坐→离座。另一方向仅翻转 `FrameVisual`，不是第二套帧或骨骼 | B04、C 十格、D01 |
| 板凳与场景元素 | `BENCH_01` 独立座点、后/前片。板凳移除前安全退出坐姿。树、花草、灯笼各一独立可开关对象，动态部分骨骼；隐藏时附属光/VFX 同清 | B04、B05、B08–B09 |
| UI/对话 | 正式身份组件与对话容器共源；Lab 导航、状态选择和诊断隔离。对话严格使用 Product 已批准的一轮演示文案，打开→第一句→第二句→关闭，重置清进度 | B06、B07、D07 |

幽灵帧播放由一处状态控制独占写入 SpriteFrame。切态先停止旧 Clip/帧计时器、位移、Tween、完成回调并递增会话/状态令牌；一次性情绪播完进入对应保持帧，不能跳回无关动作。方向切换仅改 `FrameVisual.scaleX`；世界位移方向、座点、地影、灯照、碰撞/点击区及所有文字/UI 在非镜像根上。进座先确认板凳存在且可用，停水平位移，靠近世界座点后落座；坐中转向、连续快切、撤凳、返回或卸载走同一安全退出路径。实际帧频、采样率、trim/pivot/offset 和两向接触由正式帧图及 Creator 实测决定，不能凭概要判通过。

镜头采用水平平移和正交缩放。鼠标拖拽/滚轮与触控拖拽/双指缩放转成同一相机中心和缩放操作；根据真实可绘范围与当前宽高比重算 `visibleHalfWidth/visibleHalfHeight`，中心约束在 `[left+visibleHalfWidth, right-visibleHalfWidth]`，垂直中心锁定或受绘制高度约束。若合法区间为空，停止该缩放并交 Art/Tech 复核背景覆盖，不露白、不拉伸概念图。对话浮层优先于导航/托盘，后者优先于场景；UI 捕获指针后不传播世界拖拽/缩放。竖屏 720×1280 与横向长街的视野、桥口和小字可读性须在目标设备验证，暂不更改屏幕方向。

遮挡采用明确前后片与地面支点，而非一张全桥前景 Sprite。远景/河水→桥/栏杆/店/凳后片→按脚点的顾客与孟桃→店前柜/凳前沿/桥前栏/近栏→局部世界光影与 VFX→屏幕 UI；实际跨层排序在 Creator 运行后以桥坡、店前、栏杆、板凳两向关键位置校准。世界光影不随幽灵反向镜像。

## 4. 资源与平台门禁

每一正式资源批次先有原创可编辑母版、参考及商业使用/修改/嵌入/分发权利记录，**正式出图前** Art 与 Tech 按对象/源版本共签尺寸、帧/分件、图集页数、透明边、材质、合批和内存，再导出。输出后核实际 hash、动画/图集、Creator 导入与 `.meta` UUID，登记 Prefab 依赖。动态孟桃、店件、树花灯每骨骼对象附件一页；幽灵是序列帧，实际图集页数按草排和设备实测决定。同 atlas 不保证一 DrawCall。字体许可未知、旧 Demo、概念图或未批准图稿不得用占位方式进入正式新菜单。逐项门禁与缺失处理见 [资源门禁矩阵](ASSET_GATE_MATRIX.md)。

目标先在本工程 Creator 与 Web 检查加载、状态、双入口同源，再在获批的微信/抖音目标设备复核。平台 SDK、网络和服务器协议不变；发布目标、真机机型、屏幕比例、帧时/DrawCall/纹理内存硬阈值仍待开工审批和设备清单锁定，未锁前记录原值与 `NOT_TESTED`，不能自报达标。

## 5. 性能、日志和验证

所有动画、Tween、计时器、事件订阅、异步加载和 VFX 必须归属当前 Scene 会话或对象实例；离开/卸载先禁止旧回调再清理。优先事件或动画完成回调，避免每对象空转 Update 和每帧临时数组/对象；若确需 Update，仅在活动期且记录频率。按背景、店、孟桃+顾客+凳、树花灯全开/对话、逐项清理五级负载，在固定相机位置保留冷加载、稳定和快切记录。实际记录 p50/p95/p99 帧时间、FPS、DrawCall、CPU/GPU（可得时）、真实 atlas 页数与格式、纹理驻留/峰值、节点/骨骼/粒子数、透明过绘及缓存回落。不能用 PNG 文件大小代替显存或用同图集推断批次。先测再定是否需要对象池、懒加载或经 Art/VFX 批准的非必需效果降级；不可删必验五状态、店灯影联动和三类独立元素。

日志中文描述，保留稳定模块标记如 `UNIT_MENU`、`GHOST_STATE`、`ASSET_GATE` 和可检索错误码：进入/重置/离开、资源未就绪、状态取消、座位失效、旧回调被弃、同源校验差异。日志不作为视觉或性能通过证据。Lab 应能显示当前入口/状态/资源版本，不能让诊断层进入正式对象 Prefab。

## 6. 实施顺序、回滚与待评审项

1. Client Feature Brief 与 QA Test Plan、用例完成交叉 Review，Tech Review 通过，由 Master 提交用户批准；未批准不得进入正式七项编码。
2. Art/Tech 按批次出图前联签并交付获批正式资产；每对象通过版权、源、导出、Creator 导入和版本身份门禁。可先准备 Lab 路由技术骨架的设计，但正式视觉接入必须等对应资产获批；运行菜单不得用旧图或程序形体冒充完成。
3. 在获批开工门禁后先实现共用背景/相机与 1/7 空初态，再按可用资产接入 2、3A、3B、4、5、6；各独立项与组合项立即使用同一 Prefab/状态逻辑，最后作跨入口重置、遮挡、性能和目标设备取证。资源未就绪项保持禁用并明确说明。
4. Client 提交代码、`IMPLEMENTATION_REPORT.md`、源 UUID/依赖/实例覆盖清单和实际测量；Tech 代码健康 Review，QA 执行后提交 TEST_REPORT 并待用户确认。

回滚粒度为新 `labs/menu/` 路由、各正式 `units/` Prefab/组件与导入资源的获批版本；旧九项历史文件不做删除/覆写。若资产某批退回，禁用其新入口而保留其他已过门禁的独立项，组合也不得加载该批。版本变化重新扫描依赖与两入口一致性，不静默覆盖已批准源。当前风险：长街与竖屏裁切、双向坐姿与遮挡、真实图集/骨骼导入及版权许可、目标机型和硬阈值未锁。以上均未实测。

## 7. 与 QA 的共同验收索引

`A01–A03` 对应七入口、复位、空景；`B01–B09` 对应七项及遮挡；`C` 为幽灵左/右×五态十格与转态/撤凳；`D00–D07` 对应正式源、动画方式、出图联签、同源、版权、目标设备、工具版本与禁止新增玩法。QA `TEST_PLAN.md`/`CLIENT_TEST_CASES.md` 应使用相同索引、区分规格检查和运行实测，确保每一项有目标入口、操作、预期、证据与未测状态。未来主体第三入口实际接入验证保持 `NOT_TESTED`，不影响单元阶段对独立/组合双入口的真实验收。
