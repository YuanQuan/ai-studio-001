# 三类奶茶配置迁移与兼容建议

版本 v0.1｜`PROPOSED`，待 Tech Review 与用户批准后才可执行；本轮不修改正式源表、字段说明、生成器、U05 代码或存档。当前 U05 `config.json` 仍是五维旧版：茶／奶／小料各 4 种现实原料，另有甜度、冰量；`recipe_dims` 为 3/4/5，`options_per_dim` 是所有启用维度共用数值，配方带 `sweet_id`／`ice_id`。该文件不能手工改成新方案并作为正式运行值。

## 建议的公共源迁移顺序

1. 保留已批准 v0.1 人工源与运行资源的历史快照，不覆写原归档。新建受控候选版本及完整差异记录，只有获批后才提升为正式无版本名源；索引、发布状态由既有配置契约处理。
2. Product 在新版人工源中把原料业务池改为 `TEA` 三项、`MILK` 三项、`TOPPING` 六项，使用 `CONTENT_PLAN.md` 的新 ID；旧现实原料、`SWEET`、`ICE` 不纳入新版有效出题池，也不把旧 ID 改义复用。四逻辑表保留难度阶段、解锁、原料、配方的业务关系，具体列迁移由 Product 字段字典提出，Tech 校验类型、引用和导出。
3. 阶段表的统一 `options_per_dim` 无法表达 2/2/3、3/3/6，应改为可逐类表示的开放池引用／数量；十阶段逐项引用表中完整开放名单。新版固定每杯三类，不让旧 `recipe_dims=4/5` 或 `sweet_id`／`ice_id` 进入生成结果。旧时间、三杯目标、经验阈值和奖励值保持，且阶段选择仍按旧规则。新字段中文独立说明须解释默认值、适用阶段、ID 引用及开放池上限，并与工作簿同版归档。
4. 配方池对每阶段只引用其当时开放的三类 ID，目标杯图层组合与配方三元组一一对应；新增原料要可成为目标。生成器先验证每阶段正确项在开放池、容量不超 3/3/6、组合可唯一映射到三类图层，再从已批准正式公共源生成前端运行资源。Client 只消费生成结果，不手写十二种名称、开放表、配方或旧五维回退数据。
5. Tech Lead 确定实际字段类型、生成版本、资源路径、旧版本隔离和存档兼容策略；Art/UI 对杯内三层可辨和帮助呈现分别审批。当前 U05 单元示例由 Owner 验证完整十阶段并记录证据；升级正式功能时再按适用 QA 门禁办理。上游 Product、Tech 和具体资源审批未完成时，U05 当前试玩继续被视为旧版本，不混用两套业务语义。

## 前端已有记录兼容建议

本轮只做前端试玩，优先保留已有的累计熟练度 XP、五档通关记录、永久解锁状态，并按原阈值和条件计算进入阶段；不清零、不消耗，也不以旧配方 ID 作为新内容的继续依据。已开始但未结算的旧五维半局不恢复到三维局，重进新局从第一单开始；旧结果不得重复发经验。若旧本地记录格式无法区分已结算与半局，Tech 需先提出可回滚的迁移与验证方案，不能猜测写回。旧 `source_sha256`、批准版号及五维配方不能伪装成新三维批准配置。具体存档字段、权威端和迁移代码不由 Product 设定。

## 审查与发布门禁

此文仅提出业务语义与顺序：新人工源及 41 字段旧说明的变动范围需形成逐字段差异、新中文字段说明、生成器校验与真实导出验证；若字段总数因三类开放池变化，按实际新 schema 全量解释，不能沿用旧数字。正式配置的 Product／Tech Review、用户批准和索引发布先于 Client 正式消费。U05 前端试玩可在获批方案范围内做隔离演示，但不得把草案硬编码成正式公共配置。
