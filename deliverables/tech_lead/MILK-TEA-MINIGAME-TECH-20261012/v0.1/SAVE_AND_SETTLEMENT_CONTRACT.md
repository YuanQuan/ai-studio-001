# 权威结算与可恢复存档契约 v0.1

本文件是供 Server/Client 后续实现和协议评审的技术方案，不是已经注册的 API、`.proto` 或数据库迁移。服务端业务模块与 `packages/protocol` 当前没有本小游戏实现。

## 会话与命令

服务端开始命令需经玩家身份和 `MT_SHOP_01` 授权校验，只接受已永久解锁档位，按服务端当前配置快照与累计 XP 选阶段，固定本局配置版本、阶段、三杯目标、时限、各维备选池、配方池和奖励值。服务端生成 `run_id`、订单序号、订单 ID、服务端开始时间和限时档截止时间；订单从本阶段合法配方池抽取，可重复。随机源由服务端管理，`run_id` 绑定已选订单与配方，不接收客户端自报的目标配方或随机种子。简单档截止时间为空。中途退出或放弃只得失败/退出终态，无 XP。运行中发布新配置时，服务端须保留旧版不可变快照，直到引用它的活跃局全部终结或超时；旧局重连、重试交杯均按本局固定版本判断，不能用最新配置重判。旧版快照不可用时返回可恢复错误，不推断成功或改变奖励。

交杯命令携 `run_id`、`order_id`、该单递增提交序号/幂等键及各启用维度一个原料 ID；服务端检查身份、当前活跃局、配置版本和订单、选项池、维度完整性、提交序号，再以**服务端接收时间**与截止时间比较，须严格 `< deadline`。网络发送时间、客户端倒计时显示和本地时间均不作为受理依据。时间到点且尚未完成目标时转失败；先被服务端受理的有效交杯顺序决定竞态。单序号重复请求返回原判定，不重复推进订单；同序号不同内容拒绝冲突。合法错杯保留当前订单、清空本杯选择、正确杯数不变、时间继续；正确杯计数一次并推进下一订单。若达到第三杯，则同一原子结算中确定通关；客户端提交的 success、XP、clear 或 unlock 值均不采信。客户端看见的配方提示、当前选择与倒计时只是交互状态，断线重连可查询服务端当前结果或订单；产品规则不保存半局成长进度，失去未结算活跃局时重新进入须开新局。

## 持久化与原子幂等

MySQL 记录每店每玩家累计 XP、各档 clear 事实、永久 unlock 集合，以及 `run_id` 唯一的终局结算记录。实现可采用独立关系表/唯一索引；具体 DDL 待 Server 设计评审。对第三杯正确提交，在一个 MySQL 事务中锁定玩家×店成长行、检查 `run_id` 是否已有终局、写入唯一终局记录、XP 增量、上一档 clear、重新计算可解锁的紧邻下一档并保存永久 unlock。事务提交后再返回成功/推送，失败则整单不生效并可用同幂等键重试。唯一 `run_id` 防重复发奖；订单序号唯一约束或等效事务序列化防重复完成杯数。经验为累计非消耗值；重复通关新 `run_id` 每局各给一次，失败/退出为零。简单初始永久开放；其余仅在上一档已 clear 且启用的 XP、等级、魂0–3、魄0–7全部满足时首次写入。外部等级/魂魄变化可触发同一检查，已 unlock 不回锁；关闭 XP 门槛时不以阶段1 `xp_from` 另加限制。外部条件数据的所有权和读取契约仍待其正式模块提供，不能用客户端上报值代替。

## 断线与恢复

Redis 可暂存活跃局、订单和连接映射，但不作为结算、XP、clear、unlock 的唯一事实。服务端实例重启或 Redis 丢失后，按 MySQL 终局记录恢复已结算结果；未有可靠活跃局记录则按产品“半局不保存”结束该局为退出/失败且不补发 XP。若采用 Redis 存活跃局，必须有不早于截止的 TTL 与服务端再校验，不依赖 TTL 事件作为唯一超时结算触发；启动/重连/交杯时均用权威时间判定。终局落库与回包之间断线，客户端以 `run_id` 查询已持久终局，再发同键交杯也返回同一终局。事务提交失败须返回可重试错误，不让 UI 本地推断通关。结果查询权限按玩家绑定；保留期、清理策略和请求消息编号由实施阶段确定，不在本方案假称已有。

## 必须实测的边界

同一交杯重发、同一 `run_id` 并发、服务端提交后断线、Redis 丢失、截止前/等于/截止后、错杯后重做、下局阶段变化、全部门槛关闭、魂魄边界、外部条件变化后永久解锁。正式 QA 默认从本地 Web 实际联调取证，再按适用发布门禁扩展；本稿静态检查不替代联调或 QA。
