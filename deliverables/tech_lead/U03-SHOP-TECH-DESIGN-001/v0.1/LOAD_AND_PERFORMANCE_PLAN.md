# U03 加载、竖屏投影与性能验证方案 v0.1

## 1. 当前证据与测量边界

当前代码采用 Cocos Creator 3.8.8，设计分辨率 `720×1280`、适宽；`UnitSampleGallery.ts` 只实现 U01。U03 没有正式六店图、图集、Prefab、构建或运行性能记录。Art Gate1 的 `720×1280` 与 `390×844` 是两组**候选模拟竖屏视口**，不是已实测结果或已批准硬阈值。`390×844` 的有效逻辑可见区会受适宽、设备像素比与安全区影响，不能只按原始宽高比例直接估牌匾像素。

## 2. 画布和投影记录方法

首图前 Art/Tech/UI 同批确定一个代表样张画布、店体统一地线、目标显示区域及牌匾可读判据；不得在资源未存在时写死六店贴图尺寸。Art 提供每份 PSD 总画布、各导出实际非透明包围盒、四边 alpha 留量、脚点、牌匾区域和最细字笔画；Tech 按实际 `width × height × bytes_per_pixel × mip_factor` 估算未压缩驻留上界，再结合 Creator 真实导入格式与运行 GPU 记录校正。透明画布面积和切图可能增加纹理开销，不能仅以看见的店宽估算。

每店按相同设计地线与**相同单位缩放规则**放入 U03 内容容器；允许六店自然宽度不同，不能为填满横向区域拉伸伞车/开架。两候选视口分别记录：实际 CSS 视口、DPR、`view.getVisibleSize()`、safe area、内容容器可用宽高、店体投影宽高、屋顶/棚伞与接地脚点、牌匾投影宽高和最细笔画像素、控件遮挡、四边透明裕量。UI 给出的可用区如容不下牌匾和店体，先复核布局和展示尺度；涉及改变已批准画面比例或牌匾设计时回 Art/Master 决策。主体游戏后续镜头必须以**同一正式资源源文件与身份**重新测自己的投影，不用 U03 单独放大图替代。

## 3. 资源加载与内存生命周期

实现期选择六店常驻或当前店加相邻店预取，要基于实际六店图尺寸、内存与切换延迟测试。最低功能要求是当前只实例化且只显示一店；预载资源不等于可见节点。六店贴图可缓存供循环快切，但离开 U03 应清理页面持有的实例、事件和请求序号；资源释放遵守 Creator 实际引用计数，不能释放仍被主体或其他页面使用的正式资源。若采用异步加载，末次请求令牌控制回调；失败有可见反馈并允许重试。加载策略的切换不得让旧店/新店同帧并显或出现错误牌匾。

每店 PNG 的压缩格式、mipmap、trim、packable/图集和采样设置由实际源图、字形边、alpha 光晕与目标平台试验决定。透明边被 trim 后仍需以统一逻辑脚点/Prefab 支点稳定地线；如果图集改变 SpriteFrame rect/offset，测同尺度重组和运行对应关系。不同材质、透明混合、牌匾/前件遮挡、UI 插层均可能破坏合批；**同图集不是一个 DrawCall 的证明**。不以估算值宣布 GPU 内存、DrawCall 或帧时已通过。

## 4. 预算确定与风险升级

Tech 在首图前写目标环境、代表样张预计最大画布/页数、PNG alpha 面积和最坏同时持有数量，和 Art 对同批次预签；预算初版只标 `ESTIMATE`。样张后用实际 PSD/PNG 文件头、alpha 包围盒、Creator 导入设置与构建产物更新，再在 Web 模拟视口测帧时、峰值驻留、纹理页/批次、从发出切换到正确画面提交的耗时及连续快切。QA 的硬阈值必须在其正式测试计划/性能预算获批后判定；本技术稿不虚构具体毫秒、MiB、DrawCall 或帧率上限。

测试负载至少包括：首次进入 01、按顺序遍历六店、01↔06 边界循环、连续快速往返、资源缺失/加载故障、返回菜单后重入、短视口/安全区、牌匾正读与不被控件遮挡。截图和性能记录须带构建 hash、浏览器/模拟设备、视口、DPR 与资源版本。当前这些运行项全部 `NOT_TESTED`。若实际数据与视觉锚点冲突，Tech 给可复核的尺寸/分页/格式或加载方案及成本，Art 描述视觉影响，由 Master 组织取舍；不得静默缩小字牌或砍掉灯光。
