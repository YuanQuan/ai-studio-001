# 孟桃奶茶店｜骨骼图集与 Creator 同源接入技术预审 v0.1

任务：`UNIT-PILOT-TECH-PREFLIGHT-001`。结论：**Art v0.1 的对象拆分与已批准 Product v0.1 相容，可进入概念评审；正式图片／图集导出尚未放行。** 本文是候选技术契约，待本 Artifact、Art 预案及 `CP-UNIT-REUSE-001` 各自完成评审和用户审批后，才可作为实现输入。没有图集、骨骼数据、目标设备清单或真机性能数据，故不承诺具体尺寸、DrawCall 或帧率。

- Art 的 `PARTS_PLAN.md`、`ART_BRIEF.md`、`ASSET_MANIFEST.md` v0.1 是出图前候选，**未获用户批准，且没有任何可集成图片或骨骼文件**。本评审只评价结构条件，不把布片造型、部件数或材质定案。
- `apps/client/package.json` 钉住 Creator `3.8.8`；`settings/v2/packages/engine.json` 已包含 `spine-3.8`。工程现有 `UnitSamples.scene` 与 `UnitSampleGallery.ts`；后者集中生成 U01–U09 页面、Sprite、图形、控制和测试逻辑，注释说明旧图片来自 `assets/demo/`。目前没有本样例的正式 Spine、Prefab 或双入口同源证据。
- Creator 3.8 官方文档列明 Spine 导入需要骨骼数据（`.json`/`.skel`）、图集描述（`.txt`/`.atlas`）和图集纹理（`.png`）；Creator 3.8 系列的 Spine 3.8 支持范围需以实际导出版本和 Web／微信／抖音构建复核。[Spine 资源文档](https://docs.cocos.com/creator/3.8/manual/en/asset/spine.html)

|---|---|---|

每个骨骼对象“一张图”是**该对象所有图像附件只有一个纹理页**，并非两个对象共用同一页，也不包含骨骼数据或 `.atlas` 文本；一个图集文件夹不等于只生成一页。正式导出须检查 `.atlas` 页数和引用路径。若一页无法满足可读性或设备限制，形成变更请求与影响评估，不自行拆页或降质。旅客四方向不是本轮资产，未来单独按方向和动作复核面积。

## 3. 图集、合批与内存判定口径

1. **排布前置数据**：每片源尺寸、像素密度、裁切和旋转许可、边缘留白／扩边、极限姿态的外扩区域、屏幕最近／最远投影尺寸。Art 给图集草排及一页利用率；Tech 在 Creator 实际导入和目标机渲染检查边缘、变形、可读性。不得先固定 `2048`／`4096` 等尺寸再要求 Art 硬塞。
2. **物理限制与估算**：按每台目标设备实际图形能力取得最大纹理尺寸；构建 Web、微信、抖音后核对选中的纹理格式与包体。未压缩 RGBA8 的基础层理论占用为 `宽 × 高 × 4` 字节；mipmap、解码缓存、运行时副本和 GPU 压缩另计，PNG 文件大小不能代表运行显存。Creator 支持按平台配置纹理压缩，但开发者工具不等于真机支持，透明边缘须逐格式检查。[Creator 压缩纹理文档](https://docs.cocos.com/creator/3.8/manual/en/asset/compress-texture.html)
3. **合批条件**：同一对象单页可避免动画附件跨纹理页切换，但不保证 Spine 内部恒定一笔 DrawCall。混合模式、材质实例、蒙版／裁切、颜色处理、插入的 UI 或静态节点、渲染顺序都可能切批。Creator 官方将 Spine 归为采用**独立内部合批机制**的组件，不能把 Spine 与普通 Sprite 的通用合批规则直接等同；两个独立对象各一张图集也不能承诺互相合批。[Creator 2D 合批指南](https://docs.cocos.com/creator/3.8/manual/en/ui-system/components/engine/ui-batch.html) `sp.Skeleton.enableBatch` 是可测选项，不是无条件开启的通过标准。[Creator 3.8 Spine API](https://docs.cocos.com/creator/3.8/api/en/class/sp.Skeleton)
4. **实测场景**：同一目标设备、平台构建、分辨率、镜头缩放、画质／纹理设置下依次记录空场基线、店铺静态、双骨骼待机、工作表现峰值、VFX 叠加和重置后。记录各阶段 DrawCall、帧时间（至少总帧、渲染与脚本可见项）、内存／纹理占用、图集纹理格式及截图或录屏；至少覆盖拟支持设备中的低档机和一种主流机。Web 预览只作功能检查，性能结论以微信／抖音目标真机为准。阈值、设备型号及可接受回退方案须后续技术预算经审批确定；本轮全部为`待测`。

## 4. Creator 同源接入候选契约

建议**一个已钉版本的 Creator 工程 `apps/client/`** 内维护独立资产和入口，先不物理拆成多个 `.creator` 工程。物理多工程会增加 `.meta` UUID、Prefab 引用、版本和导入同步成本；若后续确需跨工程发布，再评审资源包与迁移流程。Creator Prefab 可让场景实例继承同一源资产，但实例覆盖属性会产生差异，因此双入口须检查覆盖清单。[Creator Prefab 文档](https://docs.cocos.com/creator/3.8/manual/en/asset/prefab.html)

| 层 | 唯一源与依赖方向候选 | 演示与主体游戏的使用方式 |
|---|---|---|
| `assets/units/mengtao/` | 孟桃源骨骼及纹理、`MengTao.prefab`，仅持有角色视觉、动画适配和脚点；不依赖演示 UI。 | 两入口实例化同一 Prefab 与资源 UUID，不复制脚本／贴图。 |
| `assets/units/milk-tea-shop/` | 静态店身、可动件骨骼、`MilkTeaShop.prefab`；角色不烘进店铺。 | 可分别替换店铺／店长；场景或组合装配层定义工作位和遮挡锚点。 |
| 共用表现控制 | 一份“待机→工作→收束→待机”控制与事件协议，明确 `start`、`completed`、`reset`，同步角色、店铺可动件和 VFX；产品业务状态不从演示按钮推导。 | 演示控制和主体游戏入口只调用同一表现接口。建议重复触发期间**忽略且不给第二实例**，待 Client 设计确认并在报告中说明；当前只是低风险候选。 |
| 共用 UI／VFX | 后续获批的身份组件、字体／图标版本与 VFX 源资产；同一“奶茶店／孟桃”数据和表现语义。 | 两入口引用同一组件与 Prefab；测试按钮、重置和诊断层只存在 Lab 场景。 |
| Lab 场景与主体集成场景 | 独立 `MengTaoShopLab.scene` 和主体集成入口只负责装配、相机、输入来源。 | 修改上述任一正式源后双入口重建／重载，对照 Prefab UUID、动作、UI 样式及 VFX 版本；QA 留截图、录屏和依赖扫描。 |

当前 `UnitSampleGallery.ts` 既生成页面又管理 U01–U09 的资源和行为，直接叠加新样例会继续放大耦合。迁移时由 Client 在获批技术设计后新建独立 Lab 与正式 Prefab，逐项隔离旧 `assets/demo/`，保持现有历史样例可追溯；旧 Demo 图片、Prefab、UI 图稿或程序占位形体不能成为新样例的正式资源。构建时还应核对 Asset Bundle 的依赖和优先级，避免两入口意外打包同源资源的不同副本；是否启用自定义 Bundle 留待实装规模与包体测试，不在此预设。[Creator Asset Bundle 文档](https://docs.cocos.com/creator/3.8/manual/en/asset/bundle.html)

## 5. 每次正式出图前 Art + Tech 共同记录

记录 `对象 ID／源版本／概念审批版本／预定导出版本／目标平台与设备／镜头尺度／拆件清单／atlas 页数与尺寸草排／裁切扩边和透明格式／骨骼工具及版本／材质与混合模式／遮挡顺序／内存估算公式及参数／DrawCall 估算依据／可读性与真机待测项／版权来源与许可／两位评审人及日期／结论`。`估算`与`实测`不得混记。Art 与 Tech 对**概念、排布和测量计划**可以条件同意；在资料缺口补齐且两个角色明确签认前，结论只能是“未放行正式图片”。下一次改版仍逐次复核，不能沿用上版签认。

本次 Tech 对 Art 候选稿的预审：`MT_CHAR_01` 与 `MT_SHOP_MOTION_01` 的**单页边界及分件思路可继续设计**；静态店身独立的方案可继续设计。Art 与 Tech 尚未共同签认正式出图记录。正式出图仍缺概念定稿、逐件像素草排、设备能力、目标压缩格式、导入预览与双角色签认，因此**本次不构成出图许可或性能通过结论**。
