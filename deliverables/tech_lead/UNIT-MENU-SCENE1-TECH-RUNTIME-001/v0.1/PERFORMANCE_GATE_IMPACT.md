# 单元示例1｜Web 分阶段测试对既有性能门禁的影响 v0.1

任务：`UNIT-MENU-SCENE1-TECH-RUNTIME-001`。本文件对照已获用户批准的 `UNIT-MENU-TECH-DESIGN-001 v0.2/PERFORMANCE_PLAN.md` 与最新 `DEC-UNIT-MENU-WEB-TEST-005`、`CP-UNIT-MENU-WEB-TEST-GATE-002`。用户已明确选择先审场景接入方案，现阶段只做 **Web 端多个模拟手机分辨率** 测试；此前口语中的“真机测试”不指实体手机。用户的路径选择已生效，但不等于批准本版技术稿、具体浏览器矩阵或性能数值。按项目事实优先级，最新项目决定高于旧已批 Tech v0.2 的冲突条款；本任务 v0.1 若经专业 Review 与用户批准，即作为**示例1限定范围的正式技术增量**供 Client/QA 引用，旧版其余要求保留，不需另出一个重复修订版本作为先行门禁。

## 1. 条款冲突与适用范围

| 已批 v0.2 位置/要求 | 与最新指令的关系 | 当前示例1处理 |

旧 `CP-UNIT-MENU-PERF-GATE-001` 是历史 `PROPOSED`，其中“先审结构”的想法被最新决定采纳，但实体机型号与真机门禁提法不能继承为本阶段条件。`DEC-UNIT-MENU-WEB-TEST-005` 是当前项目决定；本影响分析与同版 `TECH_RUNTIME_SPEC.md` 构成示例1的版本化技术增量，待本版审批后按此范围覆盖旧 Tech v0.2 的冲突语句。旧版文件及其历史审批不改写，七菜单其他范围若需修订再另出新版本。

## 2. 分阶段门禁建议

### A｜现在：场景接入方案审核

以同版 `TECH_RUNTIME_SPEC.md` 为 Tech 方案，先完成 Tech 专业 Review、Master Review、用户审核。Client 后续 `FEATURE_BRIEF` 与 QA `TEST_PLAN` 也需各自 Review 和用户审批，明确先行范围为四层获批图片导入、示例1竖屏场景、水平视差、缩放/复位和 Web 可获取的运行证据。此时不需提供实体手机型号，也不因尚无 Web 硬阈值而拒绝**方案审核**。正式 Client 编码仍须等该技术方案与开工包获批；当前不能把 Gate2 的批准直接当 Client 开工批准。

Client Brief 应锁定实施用 `zMin/zMax`、初始相机状态、Web 输入方式、SpriteFrame 导入/资源身份、S03 容差与异常处理；本技术稿的 `1.0–1.8` 只是候选，不因分阶段路径自动成为正式倍率。Client 在开工包中附依据供 Tech/Product 评审与用户审批；若正式倍率影响已批体验或获批切图画面，应附同尺度视口图说明。

### B｜运行验收前：Web 矩阵与性能预算另审

Tech/Client/QA 在运行验收前提交一个可复验版本，至少列出：Web 构建 commit、Creator 精确版、获批 PNG hash/UUID；浏览器与版本、宿主 OS、渲染后端；至少 720×1280 设计比例和一个不同的竖屏模拟分辨率，逐项写实际视口与 DPR；设备模拟方式、鼠标/模拟触控能力和安全区假设；入口、冷/热加载、拖缩/重置脚本、并发可见物范围和采样时长；FPS、帧时间分布、DrawCall、纹理实际格式及可取得的内存/加载数据；各指标硬阈值、容许波动、失败时允许的降级及视觉审批影响。选择具体值并形成新版本供用户批准，不能把浏览器 DevTools 预设名视作实体设备事实。

`PERFORMANCE_PLAN v0.2` 的负载 A 对本示例1适用：四层背景与拖缩为本阶段基线；B–E 需要其他单元的正式资源/组合场景，保持 `NOT_TESTED`，不可要求本示例1伪造数据。性能预算批准前允许保存原始 Profiler/录屏，但不能宣布“性能达标”。同一图集、PNG 文件大小和静态内存算式均不能代替实测。若指标失败，先定位透明过绘、纹理格式回退、分辨率与 DPR、材质断批、缓存/解码峰值；任何改变获批图像像素、裁切或视觉锚点的降级先走 Art/用户变更门禁。

### C｜结果确认

Client 提交 Creator Web 实施证据、Tech 核版与技术实现，QA 按**获批** Web 矩阵运行并写明通过/失败/未测试；TEST_REPORT 经用户确认后，Master 才能给示例1在 Web 范围内的最终接受。若预算仍未获批，QA 可报告功能和画面观察，但性能项为 `NOT_TESTED/BLOCKED`，不得给完整质量 `PASS`。实体手机、微信/抖音容器及发布性能在当前阶段都明确 `NOT_TESTED`，未来需要时另立平台任务和审批。

| 角色 | 后续动作与门禁 |

| Client | 将旧 `UNIT-MENU-CLIENT-BRIEF-001 v0.1` 的实体机开工要求改成 Web 分阶段条件，明确代码先行范围、获批倍率/资源与后续性能门禁；再次专业 Review 和用户审批后开工 |
| QA | 修订旧 `UNIT-MENU-QA-PREBUILD-001 v0.1`，用 Web 模拟视口、浏览器配置与性能项待批状态替代实体机开工硬条件；在性能预算另审通过后才对数值质量给 `PASS` |
| Product / Art | 可观察四层关系、固定景物语义及 Gate1/Gate2 已批版不因测试环境澄清而变更；若旧验收表的“目标机”措辞会使本阶段误判，Product 出范围澄清/修订；任何改图仍先向用户说明区域与效果 |
| Producer / Master | 逐版记录 A 方案审批、Client/QA 开工包审批、B Web 矩阵/预算审批及最终报告确认；不能把用户选路径当作未来数值或功能产物批准 |

技术判断：分阶段 Web 路径可解除此前缺实体机型号造成的**方案审核阻塞**，同时保留运行验收的可复验预算门禁。技术上仍未核实 2172 宽图在拟测 Web 环境的实际纹理兼容、半透明边和运行负载；这些风险必须用 Creator 构建与获批 Web 矩阵取证，不以此文静态评估代替。
