# CAP-2026-09-29-GIT-AUTO-PUSH 技术评审

日期：2026-09-29
评审对象：`CAP-2026-09-29-GIT-AUTO-PUSH.json`
结论：**有条件通过。** 用户已明确授予日常修改后的持续 `add/commit/push` 权限；规则落地时需把授权范围和异常停止条件写清，避免将自动推送解释为自动同步、合并或发布任何工作区内容。

## 必须落实的边界

1. **逐仓库识别与提交。** Studio Repository 和每个 Game Repository 是不同的 Git 仓库，各自检查工作区、目标分支与 `origin`。只提交本轮获授权且已验证的文件，按白名单列出路径；不得用父仓库的全量 `git add .` 收进嵌套游戏仓库或无关改动。Studio 仓库只含 Studio Layer、标准模板及其允许的组织文档；游戏事实只入对应 Game Repository。
2. **同步次序与锁文件。** 组织级双同步涉及父、子仓库时分别提交和推送，并分别记录成功状态。当前游戏的 `.studio-lock.json` 只在实际应用某一模板 commit 的同步流程中更新；文件级双同步或新的模板 commit 出现，不等于当前游戏自动升级到该 commit。不得伪造锁文件 SHA，也不得把推送成功当作其他已存在游戏的自动同步授权。
3. **远端分歧时停止自动推送。** 本地提交后若 push 因远端领先、非快进、保护分支或权限失败，保留本地提交并报告仓库、分支与原因。不要为了完成推送自行 `pull`、`fetch`、`merge`、`rebase`、`reset`、强推或改写远端；这些动作不属于本次日常 `add/commit/push` 授权。若只是需只读检查远端状态，不能把检查扩大为改写历史。
4. **危险或改变仓库结构的操作独立授权。** `init`、clone、remote 配置、checkout/switch、branch、restore、revert、tag、删除远端、GitHub 等价写操作等，不应随“日常修改自动推送”一并放行。跨仓库推送失败时不能以其他仓库成功掩盖部分完成。
5. **状态可追溯。** Producer 应区分文件已修改、已验证、已提交、已推送四种事实，保存仓库、提交 SHA、目标分支与推送结果。提交前复核暂存内容，避免把密钥、构建产物、无关用户改动或 Project Layer 内容推到 Studio 仓库。

## 建议修改提案文字

提案摘要中“Studio 和当前及未来游戏项目持续执行”容易被理解为可自动触及所有既有游戏。建议明确：持续权限适用于用户交付给 Agent 工作、且本次任务实际修改的仓库；未来新建游戏仓库在创建授权完成后适用，其他既有游戏仍遵守 pinned 和显式同步评审。将“修改落地后直接推送”限定为已验证的本轮变更、仓库位置和远端均确认、可快进推送成功的情形。上述边界进入 `AGENTS.md`、同步策略及受影响角色约束后，可以实施。

本评审未执行任何 Git 操作，也未修改提案或规则文件。
